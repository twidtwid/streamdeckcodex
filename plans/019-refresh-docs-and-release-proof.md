# Plan 019: Refresh operator documentation and release/install proof

**Status:** IN PROGRESS — clean build identity and installed reload pending  
**Priority:** P1  
**Effort:** M  
**Risk:** Low  
**Depends on:** Plans 013–018  
**Target baseline:** integrated release candidate containing all recommended fixes

## Why

Documentation and progress claims have drifted across the stale saved-project lineage, the public lineage, the installed symlink, and connected-device observations. A final release must describe only behavior verified in the exact packaged build, distinguish automated from connected evidence, and give the user a quick way to prove which build is running and why a live value is unavailable.

## Current state and evidence

- Existing plan/progress records contain valid historical milestones but refer to different lineages and dates.
- The saved project can be linked directly into Stream Deck, so source, built bundle, installed link, and running process may disagree.
- Earlier QA language sometimes treated helper/unit success as proof of physical device behavior.
- Model/reasoning capability statements can become stale as Codex models and accounts change.
- Context and permission limitations need reason-specific troubleshooting rather than generic `UNKNOWN`/`NO DATA` advice.

## Drift check

```sh
git status --short
git rev-parse HEAD
rg -n "verified|connected|ready|UNKNOWN|NO DATA|model|reasoning|51 keys|seven pages" README.md QA.md PROGRESS.md docs plans package.json
npm run doctor -- --json
```

Expected: some claims lack a build SHA/date/test tier or describe historical behavior without lineage. Inventory every operator-facing document and package script before editing.

## Scope

- Update README, QA guide, setup/install instructions, PROGRESS, plan index, and relevant troubleshooting/release notes.
- Document the canonical source lineage and build identity.
- Document current control behavior, capability discovery, availability reasons, safety rules, and real limitations.
- Create one reproducible release checklist covering clean install, tests, audits, build, validate, pack, install/reload, doctor, and connected checks.
- Verify every command and link from a clean saved-project checkout.

## Out of scope

- New control behavior or profile redesign.
- Claiming connected success for unrun tests.
- Publishing a release/tag or pushing commits unless separately requested.
- Committing local logs, task IDs, screenshots with private content, or machine-specific paths.

## Git workflow

Create `codex/019-docs-release-proof` from the fully integrated release-candidate commit. Documentation changes should be the only functional delta. If a documented command fails because source is missing functionality, stop and fix it in the owning earlier plan rather than papering over it here.

## Implementation steps

### 1. Build an evidence ledger

For each claimed behavior, record:

- build SHA and plugin version;
- Codex desktop version;
- Stream Deck software and firmware/device model;
- test tier: unit, native fixture, generated/profile validation, packed artifact, or connected physical test;
- date and result;
- restoration/cleanup result for stateful connected checks.

Keep the ledger concise and exclude task identifiers/content. Automated CI results must never be labeled connected.

### 2. Rewrite setup around the canonical saved project

Document:

- prerequisites and supported versions;
- `npm ci`, build, native helper build, validation, link/install, reload, and unlink/recovery steps;
- how to prove the installed link points to the saved project;
- how to compare running build identity with source HEAD;
- how to recover from question-mark actions without copying bundles over source.

Use `$HOME` only in user-facing instructions where appropriate; scripts must resolve paths safely and print classified paths rather than assuming a username.

### 3. Document exact control semantics

Describe the actual key/encoder/touch-strip mapping generated by the canonical profile. In particular:

- session labels/order share one source across keys, Dial 1, and Previous/Next;
- Model and Reasoning rotate to preview and press once to apply;
- reasoning choices are model/account capability dependent;
- Ultra appears only when advertised by the selected model;
- Plan/Fast are visible-composer toggles and refuse drafts;
- Context and Usage are read-only;
- PTT cleanup and safety behavior;
- Health action is optional and not in the bundled profile.

Generate mapping tables from the canonical profile contract where possible so docs cannot silently diverge.

### 4. Replace generic troubleshooting with reason-specific guidance

Map each Plan 017 reason code to one short operator action. Examples: bring Codex foreground, grant/verify Accessibility, open a primary task, wait for fresh context, update for unsupported schema, or collect doctor JSON. State clearly when data is simply not exposed and no fix is available.

### 5. Create the release gate

The release checklist must run, in order:

1. drift/dirty-worktree and build-identity check;
2. clean dependency install;
3. full and production audits;
4. unit and native fixtures;
5. real action-event QA;
6. generated profile/asset parity;
7. typecheck/build/official Elgato validation;
8. package inspection;
9. saved-project install/reload and runtime SHA verification;
10. doctor health check;
11. explicit connected-device checklist for controls that mutate visible state;
12. restoration/cleanup proof.

The release command may automate non-mutating checks, but must stop before connected state changes unless the operator opts in.

### 6. Reconcile progress and historical plans

Update `PROGRESS.md` with the actual integrated state and next verified step. Preserve Plans 001–012 as history and mark Plans 013–019 only according to real completion. Do not rewrite historical failures as successes.

## Verification commands

```sh
npm ci
npm run audit:full
npm run audit:production
npm run check
npm run docs:check
npm run release:verify
npm run doctor -- --json
```

Then, only with explicit operator opt-in:

```sh
STREAMDECK_CONNECTED_QA=1 npm run release:verify:connected
```

Expected: the non-connected gate never mutates Codex; the connected gate identifies the exact build/environment, verifies visible postconditions, and restores all changed state.

## Machine-checkable done criteria

- [ ] Every operator-facing command exists and passes from a clean install.
- [ ] README/profile mapping is generated or parity-tested against the canonical 51-key contract.
- [ ] No documentation claims an exact model/effort is universally available.
- [ ] Every connected claim includes build SHA, versions, date, postcondition, and restoration result.
- [ ] Non-connected release verification performs zero Codex mutations.
- [ ] Running plugin build identity equals release-candidate HEAD/version after reload.
- [ ] PROGRESS and plan index reflect actual, not aspirational, status.
- [ ] No committed evidence contains private task content, IDs, full paths, or transcripts.

## STOP conditions

- Any documented command fails or disagrees with actual package scripts.
- Source, built bundle, installed link, running build identity, and release candidate do not agree.
- A connected verification cannot restore the original visible state.
- The visible composer contains a draft.
- A claimed physical result was not observed on the connected device for the exact build.
- Documentation would require publishing private logs or user content.

## Maintenance notes

- Treat build identity plus doctor output as the first-line support bundle.
- Expire connected evidence whenever plugin SHA, Codex version, Stream Deck version, firmware, or profile contract changes.
- Keep capability documentation dynamic and avoid version-specific promises unless tied to dated evidence.
